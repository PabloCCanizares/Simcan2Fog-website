Placement Strategies

Multi-tier resource selection

Two levels of placement

Placement happens twice for every VM. First, the CloudProvider picks which node (across zones) should host it — global placement. Then that node's ResourceManager picks which blade inside it — local placement. Each level has its own, independently configurable strategy.

FirstFit · BestFit · WorstFit

Given blades with [40, 32, 64, 16] free cores and a VM that needs 24, the three strategies land on three different blades:

Global selection & zone fallback

The CloudProvider only considers nodes in the request's zone. If none fit, it falls back to the defaultZone (typically "cloud") — the mechanism behind fog→cloud offload. It then optimistically subtracts the cores and forwards. See the DataCentre & Cloud page for the full flow and the stale-state race it can cause.

Configuration & evaluation

Strategies are NED parameters, so you can sweep them with OMNeT++ config inheritance and compare result files:

omnetpp.ini
[Config Base]
network = FogCloudScenario

[Config FirstFit]
extends = Base
**.resourceManager.selectionStrategy = "dc::FirstFit"

[Config BestFit]
extends = Base
**.resourceManager.selectionStrategy = "dc::BestFit"

# Differentiated service: priority users skip the queue
**.cloudProvider.dispatchPriority = true

Common pitfalls

Head-of-line blocking

FIFO dispatch means a big queued request blocks small ones, causing artificial rejection despite free capacity.

Unexpected zone fallback

Requests for "fog-us-west" silently land in the cloud when fog fills — set defaultZone empty for strict isolation.

Global/local mismatch

Stale global estimates dispatch to exhausted tiers; NodeUpdate eventually corrects, but you'll see oscillating success.

Custom strategy not found

Wrong namespace (dc::) or a missing Register_Class → Class not found at init.

EdgeUser & EdgeTile

Demand side of fog simulations

Overview

The EdgeUser is the demand side of fog simulations, playing a dual role: it acts as both a cloud consumer (deploying VMs via the Message Queue) and a local IoT controller (managing sensors and actuators via serial connections to a Raspberry Pi).

The EdgeTile is a compound module that packages an EdgeUser together with an EdgeNode, wireless medium, sensors, and actuators into a self-contained deployment unit.

Fault Isolation

Cloud failures do not affect serial communication. The EdgeUser's two communication paths (MQ via NetworkStack and serial to controller) are completely independent, ensuring local IoT operations continue even when cloud connectivity is lost.

Gate Interfaces

EdgeUser exposes four gates reflecting its dual role — a cloud path (TCP/IP through a NetworkStack + message queue) and a local path (a lightweight serial link to the controller). The two are fully independent: a cloud outage never blocks the local control loop.

queueIn / queueOut

Message Queue communication via NetworkStack. Used for cloud operations: VM requests, deployment commands, and status responses. Requires TCP/IP connectivity.

serialIn / serialOut

Direct connection to the local controller (Raspberry Pi). Used for local IoT operations: sensor data, actuator commands, and SM_AppSettings notifications. No TCP overhead.

VM Deployment Workflow

1

Parse Configuration

EdgeUser reads VM definitions, remote apps, and local apps (with dependsOn) from omnetpp.ini parameters.

2

Request VMs

Sends SM_UserVM messages to the "cloudProvider" topic via the MQ. Each request specifies zone, VM type, and resource requirements.

3

Deploy Remote Apps

Once VMs are confirmed, deploys remote applications (e.g., ServiceEndpoint) on the assigned DataCentre blades.

4

Notify Local Apps

When a remote service reports UP, sends SM_AppSettings via serial to the local controller, triggering local apps that depend on it.

The dependsOn Mechanism

A local app can declare a dependsOn field naming a remote app it needs. The value must match a remote app's name — the code compares strcmp(remoteApp.name, localApp.dependsOn), so there is no separate “service name” field. The local app stays PENDING until that remote app reports UP, at which point the EdgeUser pushes SM_AppSettings over serial with the service URL name.domain.

omnetpp.ini — dependsOn matches the remote app name 
*.user.vms = [{"name":"my-vm", "type":"VM_small"}]

*.user.remoteApps = [{
  "name": "my-service",            // ← the dependency target
  "type": "SmallIotService",
  "platform": "my-vm"              // ← must match a vms[].name
}]

*.user.localApps = [{
  "name": "local",
  "type": "SmallIotApp",
  "dependsOn": "my-service"         // ← equals remoteApps[].name
}]

EdgeTile

EdgeTile is a compound module packaging a complete edge deployment — seven submodules wired across three communication domains (serial, queue, wired) plus a wireless medium, exposed through a single external ethernet uplink gate.

user

EdgeUser — VMs, apps, sensors

controller

EdgeNode — local edge compute

netStack

NetworkStack — cloud uplink + queue

router

Router — local ↔ external IP

sensor[] / actuator[]

LuminositySensor · WirelessHost

radioMedium

802.15.4 narrowband PHY

LightEdgeTile — optimized variant

Swaps the Router for an EthernetSwitch and uses Eth100M links (faster L2 sims, fewer artificial bottlenecks). Adds a per-tile serviceName for multi-tenant scenarios and an optional enableRouterAsUplink when L3 isolation is needed.

EdgeTile enables scenarios like SmartBuilding, SmartCity, Industrial IoT, and Smart Farming — instantiate a tile array and connect each tile's ethernet gate to the fog/cloud network.

Key Parameters

*.user.deploymentZone = "us-east-1"
*.user.vms = [{"name":"vm-1", "type":"VM_large"}]
*.user.remoteApps = [{"name":"svc", "type":"ServiceEndpoint", "platform":"vm-1"}]
*.user.localApps = [{"name":"cli", "type":"ProbingEndpoint", "dependsOn":"svc"}]
*.user.sensors = ["sensor1", "sensor2"]

User-Centric Metrics (QoE)

EdgeUser turns infrastructure counters into quality-of-experience outcomes — distinguishing infrastructure success (a VM was allocated) from user success (the full service stack is operational).

Deployment success

Fraction of users with all VMs and apps in UP. A high VM-acceptance rate can still mask low user success if app deploy or dependsOn resolution fails.

Service availability

Time with all services UP, after warm-up:

A = Tup / (Ttotal − Tstartup)

Response time

Tlocal+Tnet+Tproc+Tret — watch tail latency (p95/p99), not just the mean, for interactive services.

Common Pitfalls

SymptomCause & fix
JSON parse error (“expected object”)Missing quotes / bad nesting / trailing comma — validate the JSON; quote every string
“App platform 'x' not found”platform must equal a vms[].name exactly (case-sensitive)
Local app stuck PENDINGdependsOn names a non-existent remote app, or a cycle — must equal a remoteApps[].name; keep a DAG
“No sensors matched pattern”Pattern doesn’t match module names — use sensor* or sensor[0..3]
“gate not connected” on queueOutWire queueIn/Out ↔ netStack and set netStack.nodeTopic

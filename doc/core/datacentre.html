DataCentre & Cloud

Physical infrastructure and stateful orchestration

Overview

The cloud tier in Simcan2Fog provides abundant capacity and centralized coordination. It consists of two complementary modules: the DataCentre (physical infrastructure) and the CloudProvider (stateful orchestrator).

Together they handle VM provisioning, application deployment, and resource management at cloud scale, typically offering 8x the capacity of the fog layer.

Key Difference from FogNode

DataCentre uses NetworkStack (flat network), while FogNode uses RoutingNetworkStack (IP routing). This reflects the architectural difference: data centres sit at network endpoints, fog nodes act as routers.

DataCentre Module

The DataCentre represents the physical infrastructure of a cloud deployment zone. It contains compute blades, a resource manager, and networking components.

Blade Arrays

Configurable number of compute blades, each with dedicated CPU cores, RAM, and disk. Cloud: typically 20-40 blades (16 cores, 64GB RAM each). Fog: typically 4-10 blades (8 cores, 16GB RAM each).

ResourceManager & NodePool

Tracks blade availability, allocates compute resources for VM requests, and manages the lifecycle of hosted applications.

AppProxy & ServiceTable

Each DataCentre includes an AppProxy for service routing and a ServiceTable for endpoint registration. Deployed services register themselves automatically.

DcManager

Coordinates internal operations: receives deployment requests from the CloudProvider, allocates blades, and reports status back through the Message Queue.

Key Parameters 
# DataCentre — instance is usually named "dc"
*.dc.numBlades = 40
*.dc.zone      = "cloud"
# domain defaults to fullName() + "-" + zone + ".com"
# the MQ topic comes from the stack (defaults to the node name)
*.dc.stack.nodeTopic = "dc"

# Per-blade capacity — aggregated by the node (40 × 16 = 640 cores)
*.dc.blade[*].numCpuCores = 16
*.dc.blade[*].memorySize  = 64GB

# Send NodeUpdate events to the CloudProvider
*.dc.dcManager.hasCloudEvents = true

CloudProvider Module

The CloudProvider is the stateful orchestrator that consumes VM requests from the Message Queue topic "cloudProvider" and coordinates placement across DataCentres. It extends StandardHost and composes three submodules:

NodeDb

Global state database tracking all DataCentres, their zones, available capacity, and hosted VMs. Used for placement decisions.

Best-Fit Placement

Selects the DataCentre with the most available cores that still satisfies the request. Zone-aware: only considers DataCentres in the requested deployment zone.

Orchestration Flow

1

Receive SM_UserVM

CloudProvider pulls a VM request from the "cloudProvider" MQ topic.

2

Select Target via NodeDb

Queries NodeDb for DataCentres in the requested zone, applies best-fit selection by available cores.

3

Forward to DataCentre

Sends the VM request to the selected DataCentre's MQ topic for provisioning.

4

Respond to User

Once the DataCentre confirms provisioning, CloudProvider sends the response to the user's returnTopic.

The full request cycle

NodeDb: the global state database

Every placement decision reads from NodeDb, which wraps a NodeTable of three parallel structures — one for the resources, one indexed by topic (for forwarding), and one indexed by zone (for zone-aware placement).

Key methods: addOrUpdateNode() (upsert on a NodeUpdate), findNodeByTopic(), findNodesByZone(), getNode(), and getTopicForNode(). You can watch this table live in Qtenv via its WATCH macros to spot staleness against the real DataCentre state.

Placement: best-fit with zone fallback

Given a request, the provider looks only at DataCentres in the requested zone, picks the best fit (the candidate with the most free cores that still satisfies the request), and optimistically reserves the cores before forwarding. If the zone can't serve it, it falls back to the defaultZone.

⚠️ Optimistic reservation

The provider subtracts the cores before the DataCentre confirms. If the DataCentre later rejects (its real capacity was already taken), it must send a corrective NodeUpdate to "uncommit" — the root of the stale-state race below.

Keeping state in sync: NodeUpdate

The provider never reads a DataCentre directly. Instead each DataCentre pushes a NodeUpdate whenever its availability changes, carrying an absolute snapshot of free cores, RAM and disk.

Saturation: queues & failure modes

When every candidate is full, a user can subscribe (SM_VM_Sub) and wait. The provider queues the request with a timeout and retries it the moment capacity frees up.

Common failure modes

State staleness & double allocation

The provider's belief drifts from reality (see the race above). Symptoms: rejections despite "enough" capacity, or exhaustion despite "available". Mitigate with more frequent or periodic updates.

Control-plane bottleneck

Every request funnels through one cpService. Under load it saturates — rising end-to-end latency and growing queues despite free blades. Watch processing latency vs network latency.

Zone misconfiguration

If defaultZone names a zone with no registered DataCentres, every request fails hard (the provider raises an error) — even if other zones are idle.

NodeUpdate loss

Updates ride the Message Queue with no acknowledgement. A lost update leaves the provider permanently stale; a periodic background refresh bounds the staleness window.

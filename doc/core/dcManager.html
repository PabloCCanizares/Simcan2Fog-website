DcManager

VM lifecycle orchestration

The orchestration layer

The DcManager is the broker between external requests and internal execution. It interprets allocation decisions, dispatches VM-instantiation commands to individual blade hypervisors, manages VM rental timeouts, and keeps the CloudProvider in sync. It lives inside every DataCentre and FogNode, extending a shared ManagerBase.

Dispatches VMs

Turns allocations into hypervisor commands.

Manages rentals

User-controlled extend / release timeouts.

Syncs the cloud

Emits NodeUpdate on capacity changes.

Two networks, four gates

The DcManager straddles two fabrics: the Message Queue (for inter-node coordination) and the node's internal switch (for talking to blades).

Routing by callback, not by switch

Instead of a giant switch, every message is dispatched through one of three handler maps keyed by op/result code — so new operations are just a map insertion.

Deploying a VM

A request becomes a blade command through capacity check, dispatch, and hypervisor URL addressing of the form "node::blade" (e.g. dc1::blade5).

VM rentals: the extension protocol

VMs are rented, not permanent. As a rental nears expiry, a three-message negotiation lets the user extend or release — termination is never automatic.

Sync & monitoring

CloudProvider sync

A NodeUpdate is sent on four events: initial registration, allocation reject (uncommit), subscription reject, and VM release. Acceptances are tracked through ResourceManager signals instead.

See the full sync model on the DataCentre & Cloud page.

Utilisation & forecasting

Periodic CPU_STATUS and MANAGE_MACHINES timers log usage at cpuStatusInterval. With forecastActiveMachines, single exponential smoothing predicts demand.

⚠️ setActiveMachines() is still a stub — dynamic power management is a known extension point.

Common pitfalls

"Wrong node" on URL resolve

A hypervisor URL routed to the wrong DataCentre/FogNode. Multi-hop routing needs nodeName rewriting at tier boundaries.

Accept then dispatch fails

Blade hostnames in netDb don't match generateHypervisorUrl — verify registration names.

Map memory growth

acceptedUsersRqMap is never pruned — long runs leak. Add cleanup in the termination handler.

Cloud overcommit

Missing sendUpdateToCloudProvider calls leave stale high-capacity estimates → overcommitment.

Application Protocols

RESTful message flows

A lightweight REST

Application traffic uses a simplified RESTful model — the essential HTTP semantics (a verb, a host, a path, a status code) without the weight of a full HTTP stack. It maps cleanly onto service-oriented fog architectures, where clients address named services rather than raw IPs, and keeps simulations fast at scale.

⚠️ It does not model HTTP/2, head-of-line blocking, pipelining or server push. For those, extend the protocol or use INET's HTTP models.

Message structure

Verbs

  • GET read · POST create
  • PUT update · DELETE remove
  • HEAD metadata / health-check probe

Response codes

  • 200 OK — success
  • 403 NOT_FOUND — service unavailable / unregistered
  • 503 INTERNAL_ERROR — server-side failure

Request → response

A client resolves the service (DNS or ServiceTable), connects on :443, sends a RestfulRequest, and the proxy routes it to a registered backend that replies.

The AppBase API

Applications don't touch raw INET sockets — AppBase wraps the lifecycle plus service registration and DNS.

Socket lifecycle

open() → connect()
/ listen() → _send()
→ handleDataArrived() → close()

Become discoverable

registerService(name, fd) sends a ProxyServiceRequest so clients can reach you by name.

Resolve names

resolve(domain) hands off to the StubDnsResolver (async callback).

ServerEndpoint.cc
int fd = open(443, SOCK_STREAM);   // bind + TCP
listen(fd);                       // accept connections
registerService("dataProcessor", fd); // → ServiceTable
// now clients can GET dataProcessor.us-east-1.com

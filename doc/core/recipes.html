Scenario Recipes

From zero to running experiments

Copyable templates drawn from the showcases/ and simulations/ directories. Each recipe gives an objective, the minimal topology, the essential omnetpp.ini parameters, and what to expect — so you can bootstrap without decoding the whole codebase.

The recipe ladder

1

Single DataCentre with Remote Users

showcases/dc

Objective — minimal one-zone deployment: DcUser modules request a VM, deploy an app, and run a CPU workload over REST. Validates ResourceManager capacity accounting and DcManager orchestration without multi-tier complexity.

omnetpp.ini — essentials
network = DcShowcase
*.dataCentre.numBlades          = 4
*.dataCentre.zone              = "us-east-1"
*.dataCentre.blade[*].numCpuCores = 16   # 4×16 = 64 cores

*.dcUsers[*].edgeUser.deploymentZone = "us-east-1"
*.dcUsers[*].edgeUser.vms = [{"name":"vm-us-east-1","type":"VM_large"}]
*.dcUsers[*].edgeUser.remoteApps = [{"name":"huge-calculation",
    "type":"AppCPUIntensive","platform":"vm-us-east-1"}]

Expect to see

  • • maxCores = 64 at init
  • • SM_VM_Res_Accept on allocation
  • • Hypervisor URL "dataCentre::blade[i]"
  • • Verb::GET → ResponseCode::OK
2

Cloud-Fog-Edge Multi-Tier with Offloading

simulations/EdgeScenario

Objective — EdgeUsers prefer fog but tolerate cloud offloading when fog saturates. Exercises zone-aware placement and fallback to defaultZone across InternetCloud delay tiers.

omnetpp.ini — zone fallback
*.cloudProvider.defaultZone = "cloud"
*.fg.zone = "edge"   *.fg.numBlades = 10  # 10×8 = 80 VM cap
*.dc.zone = "cloud"  *.dc.numBlades = 40

[Config targetFog]
*.user.deploymentZone = "edge"     # prefer fog, fall back to cloud

Under load past 80 fog VMs, selectNode logs “No suitable nodes in zone: edge → defaulting to zone: cloud” and URLs flip from "fg::blade[i]" to "dc::blade[i]" — latency jumps as traffic takes the backbone path.

3

IoT Integration with Local Controllers

dual-socket

Objective — one EdgeUser drives both cloud VMs (processing) and local IoT devices (sensing/actuation). A Raspberry5 intermediates over serial, while cloud traffic uses the queue path — two sockets, no protocol confusion.

Serial path (local)

user.serialOut → controller.serialIn
sensor → Raspberry5 → EdgeUser

Queue path (cloud)

user.queueOut → netStack → MQ
EdgeUser ↔ my-service (VM)

omnetpp.ini — dependency chain
*.user.sensors   = ["sensor"]
*.user.remoteApps = [{"name":"my-service","type":"SmallIotService",
    "platform":"my-vm"}]
*.user.localApps  = [{"name":"local","type":"SmallIotApp",
    "dependsOn":"my-service"}]   # local waits for cloud
*.sensor.model.controllerPath = "^.^.controller"

EdgeUser delays the local app until my-service registers in the ServiceTable — the dependsOn edge gates startup so sensing only begins once the cloud processor is reachable.

4

Controlled Scaling Without Results Explosion

showcases/fog

Objective — hundreds of users and thousands of VMs while keeping result files under control. The trick: UserGenerator for dynamic users, a warmup-period, and selective recording that aggregates instead of dumping raw vectors.

omnetpp.ini — slim results
sim-time-limit = 24h     warmup-period = 1h

**.vector-recording = false            # off by default…
**.resourceManager.allocatedCores.vector-recording = true  # …on for the few you study
**.resourceManager.*.vector-recording-intervals = 0..3600, 21600..25200

# aggregate at the source — never store raw vectors
*.dc.blade[*].cpu.utilization:vector.result-recording-modes =
    -vector, +histogram(0.0, 1.0, 20)
**.cloudProvider.queueLength:vector.result-recording-modes =
    -vector, +min, +max, +mean, +stddev, +count
Result: 1000 users · 10,000 VM requests · 24 h simulated — yet result files stay under 1 GB and postprocessing finishes in minutes. The warmup-period drops startup transients; histograms/stats replace gigabyte time series.

Sanity signatures

Before comparing policies, confirm each run shows the expected behavioural shape.

Capacity accounting

∑ allocatedCores ≤ maxCores at all times. A violation = RM/NodePool accounting bug.

Utilisation curve

Logistic 0% → steady-state under constant arrivals. >100% or wild oscillation = scheduler / CPU-speed misconfig.

Queue dynamics

Sawtooth under overload (grow → drop on VM release). Monotone growth = missing NodeUpdate/termination.

Latency distribution

Multimodal: ~1–10 ms (fog), ~50–100 ms (cloud), 500 ms+ tail (overload). Single mode = fallback failure.

SymptomCause & fix
Unreachable subnetsOverlapping IPs — give each component a non-overlapping configurator.config range

Universal rejectionnumBlades × maxVMs must exceed peak demand (5×4=20 can't serve 30)
“VM type not found”Every referenced type must exist in apps.json / vms.json

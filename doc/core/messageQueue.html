MessageQueue

Topic-based messaging broker for fog systems

What is MessageQueue?

MessageQueue is a messaging broker (similar to a central message bus) modeled as a real INET host that extends StandardHost and receives/delivers messages over TCP.

Its function is to be the point of synchronization and communication between system actors:

  • →EdgeUser
  • →FogNode
  • →DataCentre
  • →CloudProvider
  • →Other services

💡 Key Concept

Instead of each module knowing all others (and having direct connections), all communicate using:

  • • A destinationTopic field (which "mailbox" the message goes to)
  • • A returnTopic field (which "mailbox" to reply to)

Internal Architecture

MessageQueue has two main submodules:

📥

A) MessageQueueIn (pushServer)

TCP Port 8444

  • • Receives incoming TCP traffic
  • • Extracts application messages (INET_AppMessage) and reads the destinationTopic
  • • Forwards the message to the output component to enqueue it by topic

Purpose: This is where everything that producers "publish" enters

📤

B) MessageQueueOut (pullServer)

TCP Port 8443

  • • Maintains a FIFO queue per topic: topicToQueueMap[topic]
  • • Maintains one consumer per topic: topicToConsumerMap[topic]
  • • Delivers messages with a pull + ACK (backpressure) mechanism:
    • → Consumer requests work by sending SM_QueueAck
    • → Broker delivers 1 message
    • → Consumer sends another ACK when ready for next

Purpose: Controls consumption rate, preventing flooding

⚡ Preemptive Queue Allocation

MessageQueueOut has preemptiveQueueAllocation = true by default.

If a message arrives to a topic without a registered consumer yet, the broker creates the queue anyway and enqueues it. This is key for startups: a producer can publish before the consumer is ready.

How to Use from Nodes

Nodes don't talk to MessageQueue through "direct NED wires", but over TCP/IP using QueueClient inside NetworkStack.

QueueClient has 2 TCP connections

  • Push: PushClient + pushSocket → connects to smqIp:8444
  • Pull: PullClient + pullSocket → connects to smqIp:8443

Sending a Message (C++ Example)

Here's how to send a message through the MessageQueue from your application code:

YourApp.cc 
// Create a new SIMCAN message
SIMCAN_Message *msg = new SIMCAN_Message();

// Set the destination topic (where the message goes)
msg->setDestinationTopic("datacentre/jobs");

// Set the return topic (where replies should go)
msg->setReturnTopic("edge/responses");

// Add your payload data
msg->setOperation(SM_VM_Req);
msg->setUid(userID);

// Send through NetworkStack's queue
send(msg, "queueOut");

What PushClient does

When it receives a SIMCAN_Message from queueIn:

  1. Ensures return channel: If autoSourceTopic is active, sets returnTopic = topic (the client's nodeTopic)
  2. Encapsulates: Wraps SIMCAN_Message inside INET_AppMessage then Packet
  3. Sends via TCP: Sends it to the broker (port 8444)

What PullClient does

On startup:

  1. Generates SM_QueueAck with destinationTopic = <my topic>
  2. Sends it immediately via TCP to broker (port 8443)

When receiving a packet from broker:

  1. Unpacks the messages
  2. Emits them through queueOut to local consumer module
  3. Sends another SM_QueueAck to request next message

Example: SimpleFogNetwork Scenario

Let's trace a message from an edge device to a data centre through the MessageQueue.

1

Edge produces a SIMCAN message

The message enters netStack.queueIn and reaches PushClient.

destinationTopic = "dcTopic"
autoSourceTopic = true → returnTopic = "edgeTopic"
2

PushClient converts to TCP/IP traffic

  • • Encapsulates in Packet
  • • Opens/uses TCP connection to smqIp:8444
  • • Exits through INET stack of netStack host
3

Physical path through topology

IP traffic travels through the network:

netStack.ethg++ ← Eth100M → ap
ap ← Eth10G → local
local ← Eth10G → fg.comm++
metropolitan ← backbone
backbone ← Eth100G → sw
sw ← Eth100G → messageQueue.ethg++

⚠️ Important: No "logical wire" netStack→messageQueue, but there IS IP connectivity via routing.

4

MessageQueueIn receives and classifies

  • • Receives TCP data on port 8444
  • • Extracts SIMCAN_Message
  • • Reads destinationTopic
  • • Calls MessageQueueOut.pushIncomingMessage(topic, msg)

Result: Message enters the topic's queue

5

DC consumes using pull + ACK

Data centre's NetworkStack/QueueClient:

  • • Sends SM_QueueAck(destinationTopic="dcTopic") to smqIp:8443
  • • On receiving ACK, broker:
    • → Registers consumer if it didn't exist
    • → Delivers 1 message from the topic's queue

DC receives message through PullClient.queueOut and processes it

Key Concepts to Understand

1️⃣ destinationTopic decides routing

Messages don't go to a concrete service IP, they go to a logical mailbox.

2️⃣ Preemptive queuing

Broker can enqueue even if consumer isn't ready yet, thanks to preemptiveQueueAllocation=true.

3️⃣ Controlled consumption

The broker doesn't "push infinitely". It delivers 1 message and waits for ACK (backpressure).

4️⃣ No direct NED connections needed

Real connectivity is IP/TCP, and the path is defined by topology and Ipv4NetworkConfigurator.

Common Issues & Solutions

⚠️ Messages enqueue but don't deliver

Possible causes:

  • • Consumer isn't sending SM_QueueAck
  • • Consumer hasn't registered to the correct topic
  • • destinationTopic doesn't exactly match expected topic

⚠️ smqIp configuration

smqIp must be the real IP address of the messageQueue host in your simulation (assigned by Ipv4NetworkConfigurator).

💡 nodeTopic must be unique

Each node consumer/producer should have a unique nodeTopic if you want clean responses.

⚠️ Unbounded queue growth

With preemptiveQueueAllocation there is no TTL: if a topic has no consumer (or a disconnected one), or the topic name doesn't match, messages pile up indefinitely and simulation memory grows. Watch the "Created queue / Registered consumer" logs and verify exact topic spelling.

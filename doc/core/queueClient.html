Queue Client

Bridge between nodes and the Message Queue

Overview

The QueueClient is a compound module that bridges any node (EdgeUser, CloudProvider, DataCentre) with the central Message Queue (SMQ). It handles the TCP transport, message wrapping, and the ACK-driven subscription protocol.

Compound Module Structure

Interfaces (gates)

queueIn input

Local apps publish SIMCAN_Message instances here; the PushClient picks them up.

queueOut output

The PullClient delivers messages received from the subscribed topic to local apps here.

socketIn / socketOut TCP

Carry INET Packets to/from the node's NetworkStack, which reaches the SMQ broker over TCP.

Broker ports

pushPort 8444 (publish) and pullPort 8443 (subscribe), hardcoded in the SMQ.

Submodules

PushClient (Outbound)

Sends messages to the SMQ on port 8444. Fire-and-forget delivery. Automatically sets the returnTopic via the autoSourceTopic flag. Wraps each SIMCAN_Message in an INET_AppMessage with a 20-byte header.

PullClient (Inbound)

Receives messages from the SMQ on port 8443. Uses an ACK-driven subscription loop: sends SM_QueueAck → receives one message → delivers to node → sends next ACK. This provides natural backpressure - the consumer controls the rate.

pushSocket / pullSocket (TcpClientSocketIo)

TCP transport adapters that handle connection establishment, data framing, and reconnection to the SMQ endpoints.

qt (MessageDispatcher)

Routes messages between the push/pull clients and the node's internal gates. Handles the multiplexing of inbound and outbound traffic.

Message Flow

Publishing and subscription run independently and coordinate only through shared topic names. Publishing is one-way and fire-and-forget; subscription is a self-paced acknowledgement loop.

Push vs Pull

The two services are deliberately asymmetric — publishing optimises for latency, subscription optimises for controlled delivery.

Where it lives: the NetworkStack

The QueueClient is a conditional submodule of the node's NetworkStack (instantiated only when enableQueue is true). The stack binds two convenience parameters — smqIp → connectAddress and nodeTopic → topic — so most nodes never touch the QueueClient parameters directly. Its socketIn/socketOut gates join the at dispatcher, which multiplexes the QueueClient, DNS and apps onto the shared TCP/IP stack.

Key Parameters

The module has just four parameters — connectAddress, topic, pullPort (8443) and pushPort (8444). In practice you set them once through the NetworkStack:

# Idiomatic — configure once via the NetworkStack
**.smqIp                = "10.0.0.1"       # → queueClient.connectAddress
*.cp.netStack.nodeTopic = "cloudProvider"  # → queueClient.topic
**.netStack.enableQueue = true            # instantiate the QueueClient (default)

# Or set the QueueClient parameters directly
*.cp.netStack.queueClient.connectAddress = "10.0.0.1"
*.cp.netStack.queueClient.topic         = "cloudProvider"
*.cp.netStack.queueClient.pullPort      = 8443  # default
*.cp.netStack.queueClient.pushPort      = 8444  # default

autoSourceTopic is not a module parameter — it's a flag carried on each SIMCAN_Message that the PushClient checks to decide whether to stamp the returnTopic.

Failure modes & resilience

The QueueClient is intentionally minimal, which means most failures are silent — nothing errors at publish time. Knowing where they hide is half the battle.

① Push connection lost

Outbound messages are silently dropped. Fire-and-forget means no retry or persistence — anything sent during the outage is gone.

② Pull connection stall

The consumer hangs indefinitely. There's no pull timeout, so a silently broken pull connection waits for a batch that never comes while messages pile up at the broker.

③ Missing returnTopic

Requests succeed but replies never arrive. With autoSourceTopic off (or returnTopic unset), the service publishes the reply to an undefined topic — the requester just times out.

④ Topic name mismatch

Published but never delivered. Topics are case-sensitive exact strings, so "CloudProvider" ≠ "cloudProvider"; publishing to a topic with zero subscribers drops the message with no warning.

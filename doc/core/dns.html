DNS

Domain Name System for service discovery

What is DNS in Simcan2Fog?

Simcan2Fog includes a Domain Name System (DNS) implementation to support the discovery of hosts, services, and applications within simulated fog computing environments. DNS provides name resolution and service discovery, resolving service identifiers to IP addresses on demand.

The DNS component follows the specifications defined in RFC 1034 and RFC 1035, supporting both hierarchical resolution with caching and a simplified direct lookup mode for faster prototyping.

💡 Key Concept

Instead of hardcoding IP addresses throughout your simulation, DNS enables dynamic service discovery. Services can be registered with human-readable names, and clients can look them up at runtime, making configurations more flexible and maintainable.

DNS Architecture

Simcan2Fog provides two DNS resolution modes, each suited for different simulation scenarios:

🔀

Hierarchical Resolution

Full DNS protocol implementation

Follows the standard DNS hierarchy with root servers, TLD (Top-Level Domain) servers, and authoritative name servers. Supports recursive resolution with caching.

  • • Realistic: Models real-world DNS behavior
  • • Cached: Reduces lookup latency for repeated queries
  • • Scalable: Handles large, complex network topologies
⚡

Simplified Resolution

Direct lookup mode

Single root server where all services are published directly, bypassing the hierarchical structure. Faster and simpler for small-scale scenarios.

  • • Simple: No hierarchy management needed
  • • Fast: Single-hop lookups
  • • Prototyping: Ideal for development and testing

DNS Components

🔄

Recursive Resolver

The client-facing component that receives DNS queries from fog nodes, IoT devices, and other network entities. It performs recursive lookups by contacting the appropriate DNS servers according to the domain hierarchy.

Features:

  • • Query caching: Stores recent resolutions to reduce latency
  • • Recursive lookups: Follows DNS hierarchy automatically
  • • TTL enforcement: Respects time-to-live for cached entries
  • • Fallback handling: Retries and error management
🌍

Root Server

Top-level server in the DNS hierarchy. In hierarchical mode, it delegates queries to appropriate TLD servers. In simplified mode, it directly resolves all queries.

  • • Entry point: First server contacted in resolution chain
  • • TLD delegation: Routes queries to correct top-level domain servers
  • • Simplified mode: Can act as single authoritative server
📋

TLD & Authoritative Servers

In hierarchical mode, TLD servers handle top-level domains (.com, .org, custom domains), and authoritative name servers provide final IP address resolution for specific domains.

  • • TLD servers: Manage top-level domain delegations
  • • Authoritative servers: Store actual DNS records for domains
  • • Zone management: Handle domain-specific configurations

Supported DNS Record Types

The DNS implementation currently supports the following standard record types:

🔤 A (Address)

Maps domain names to IPv4 addresses. The most common record type for resolving hostnames to IP addresses.

example.com → 10.0.0.5

🔗 CNAME (Canonical Name)

Creates aliases by mapping one domain name to another. Useful for service redirection and load balancing.

www.example.com → example.com

📡 NS (Name Server)

Specifies authoritative name servers for a domain. Used for domain delegation in the DNS hierarchy.

example.com → ns1.example.com

✉️ MX (Mail Exchange)

Directs email to mail servers. Includes priority values for fallback and load distribution.

example.com → mail.example.com (priority: 10)

Hierarchical Resolution Example

Let's trace a DNS query through the hierarchical resolution process to understand how service discovery works in practice.

1

Initial Query

A fog node needs to contact the cloud provider manager service at cpman001.cp

The resolver cache is empty, so a full hierarchical lookup is required.

2

Query Root Server

Resolver contacts root server: "Who handles the .cp TLD?"
Root server responds with NS record pointing to TLD server for .cp domain

Response: NS for .cp → 10.0.0.10
3

Query TLD Server

Resolver contacts TLD server: "Who is authoritative for cpman001.cp?"
TLD server responds with authoritative name server address

Response: NS for cpman001.cp → 10.0.0.20
4

Query Authoritative Server

Resolver contacts authoritative server: "What is the IP of cpman001.cp?"
Authoritative server responds with final A record

Response: A cpman001.cp → 10.0.0.3
5

Cache & Connect

Resolver caches all intermediate results (root, TLD, authoritative NS) and the final IP address. Fog node establishes TCP connection to 10.0.0.3 and sends VM deployment request.

⚡ Subsequent Queries

Future queries for cpman001.cp or other services in the same domain can skip steps by using cached NS records, dramatically reducing lookup latency.

DNS Configuration

Configure DNS services in your simulation scenario:

omnetpp.ini 
# DNS Resolver Configuration
*.resolver.typename = "DnsResolver"
*.resolver.cacheSize = 1000 # Number of cached entries
*.resolver.cacheTTL = 3600s # Time-to-live for cache entries

# Root DNS Server
*.rootDns.typename = "DnsServer"
*.rootDns.mode = "root"

# TLD DNS Server (.cp domain)
*.tldDns.typename = "DnsServer"
*.tldDns.mode = "tld"
*.tldDns.domain = "cp"

# Authoritative DNS Server
*.authDns.typename = "DnsServer"
*.authDns.mode = "authoritative"
*.authDns.zone = "cpman001.cp"

# Service Registration
*.authDns.records = "cpman001.cp A 10.0.0.3"

# Simplified Mode (Alternative)
# *.simpleDns.typename = "SimpleDnsServer"
# *.simpleDns.records = "cpman001.cp:10.0.0.3,fognode1.local:10.0.1.5"

Common Use Cases

Service Discovery for Cloud Provider

Fog nodes and edge devices discover the cloud provider manager service using DNS lookups instead of hardcoded IPs, allowing flexible infrastructure changes without reconfiguration.

Fog Node Mesh Discovery

Fog nodes discover peer nodes dynamically for workload forwarding and load balancing. DNS enables flexible mesh topology management.

Multi-Tenant Service Isolation

Different tenants or experiments can use separate DNS zones, isolating their services while sharing the same physical infrastructure.

Load Balancing via DNS

Multiple A records for the same domain name can distribute load across service replicas. DNS round-robin enables simple load distribution strategies.

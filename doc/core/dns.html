DNS

Domain Name System for service discovery

What is DNS in Simcan2Fog?

Simcan2Fog includes a Domain Name System (DNS) implementation to support the discovery of hosts, services, and applications within simulated fog computing environments. DNS provides name resolution and service discovery, resolving service identifiers to IP addresses on demand.

The DNS component follows the specifications defined in RFC 1034 and RFC 1035, supporting both hierarchical resolution with caching and a simplified direct lookup mode for faster prototyping.

💡 Key Concept

Instead of hardcoding IP addresses throughout your simulation, DNS enables dynamic service discovery. Services can be registered with human-readable names, and clients can look them up at runtime, making configurations more flexible and maintainable.

DNS Architecture

Resolution is split across three real components — a client-side stub cache, a recursive ISP resolver, and authoritative servers. From a client's point of view, every query takes one of two paths:

⚡

Cache hit — stub resolver

Fast local path

Every node's NetworkStack holds a StubDnsResolver. If the name is already cached locally, it answers instantly, with no network traffic.

  • • Direct: apps call it via a direct gate (no UDP)
  • • Cheap: zero round-trips on a hit
  • • Caveat: the current cache has no TTL/expiry
🔀

Cache miss — recursive resolver

Walks the zone tree

On a miss the stub forwards to the ISP resolver (DnsResolverServer), which recursively walks the DnsDb zone tree (root → TLD → authoritative) and caches the result.

  • • Recursive: a state machine drives each step
  • • Aggregated: duplicate questions share one upstream query
  • • Cached: results stored at every tier

DNS Components

🔄

StubDnsResolver (client)

The client-facing resolver embedded in every NetworkStack. Applications call resolve() through a direct gate; on a cache hit it answers immediately, otherwise it forwards the query to the ISP resolver through DnsClientService (UDP, with retry/timeout).

  • • Local cache: stores answers at AUTHORITATIVE level for instant hits
  • • Direct API: apps reach it via resolverPath, no protocol code needed
  • • Forwarding: misses go to ispResolver
  • • Caveat: no TTL/expiry on cached entries (see Failure modes)
🔁

DnsResolverServer (recursive / ISP)

Resolves names on behalf of clients. Its DnsResolverService runs a recursive state machine that walks the hierarchy, while DnsClientService handles the outgoing queries and a local DnsDb caches answers.

  • • State machine: INIT → TLD → NS → AUTH → RESOLVED
  • • CNAME chains: follows aliases recursively to a final address
  • • Question aggregation: duplicate concurrent queries share one upstream lookup
  • • Caching: stores results to accelerate repeats
🌍

DnsSimplified (authoritative)

Holds authoritative zone data and answers queries for the domains it manages. The DnsServiceSimplified server replies on UDP :53, and a DnsRegistryService accepts dynamic registration over REST on TCP :443.

  • • Authoritative answers: distinguishes authoritative vs non-authoritative
  • • UDP :53: processes QUERY operations
  • • REST :443: POST/PUT/DELETE records at runtime
  • • Backed by DnsDb: the shared zone tree
📋

DnsDb (the zone tree)

A hierarchical tree that stores resource records across three levels — ROOT → TLD → AUTHORITATIVE. It is the single storage shared by the authoritative server, the resolver cache, and the stub cache.

  • • Preloaded: from JSON zoneConfig (see Configuration)
  • • Wildcards: patterns like *.example.com via cPatternMatcher
  • • Dynamic: CRUD — insertRecord / removeRecord / searchRecords

Supported DNS Record Types

The DNS implementation currently supports the following standard record types:

🔤 A (Address)

Maps domain names to IPv4 addresses. The most common record type for resolving hostnames to IP addresses.

example.com → 10.0.0.5

🔗 CNAME (Canonical Name)

Creates aliases by mapping one domain name to another. Useful for service redirection and load balancing.

www.example.com → example.com

📡 NS (Name Server)

Specifies authoritative name servers for a domain. Used for domain delegation in the DNS hierarchy.

example.com → ns1.example.com

✉️ MX (Mail Exchange)

Directs email to mail servers. Includes priority values for fallback and load distribution.

example.com → mail.example.com (priority: 10)

🧭 SOA (Start of Authority)

Declares the authoritative parameters of a zone (primary name server, serial, refresh). Exactly one per zone.

example.com SOA ns1.example.com

↩️ PTR (Pointer)

The reverse of an A record — maps an IP address back to a name. Used for reverse DNS lookups.

10.0.0.5 → host.example.com

📝 TXT (Text)

Attaches arbitrary text metadata to a name — handy for tagging service descriptors or experiment markers.

example.com TXT "zone=us-east-1"

🗂️ ANY (query-only)

A query type (not stored) that asks for all record types known for a name.

ANY example.com → (all records)

Record types are defined in DnsDefinitions.msg: A, NS, CNAME, SOA, PTR, MX, TXT, ANY.

Hierarchical Resolution Example

Let's trace a DNS query through the hierarchical resolution process to understand how service discovery works in practice.

1

Initial Query

A fog node needs to contact the cloud provider manager service at cpman001.cp

The resolver cache is empty, so a full hierarchical lookup is required.

2

Query Root Server

Resolver contacts root server: "Who handles the .cp TLD?"
Root server responds with NS record pointing to TLD server for .cp domain

Response: NS for .cp → 10.0.0.10
3

Query TLD Server

Resolver contacts TLD server: "Who is authoritative for cpman001.cp?"
TLD server responds with authoritative name server address

Response: NS for cpman001.cp → 10.0.0.20
4

Query Authoritative Server

Resolver contacts authoritative server: "What is the IP of cpman001.cp?"
Authoritative server responds with final A record

Response: A cpman001.cp → 10.0.0.3
5

Cache & Connect

Resolver caches all intermediate results (root, TLD, authoritative NS) and the final IP address. Fog node establishes TCP connection to 10.0.0.3 and sends VM deployment request.

⚡ Subsequent Queries

Future queries for cpman001.cp or other services in the same domain can skip steps by using cached NS records, dramatically reducing lookup latency.

DNS Configuration

Configure DNS services in your simulation scenario:

omnetpp.ini 
# Authoritative DNS server (DnsSimplified) — zones from JSON
*.dns.db.zoneConfig      = readJSON("DnsZone.json")

# Recursive resolver (DnsResolverServer) — NS records from JSON
*.resolver.db.zoneConfig = readJSON("ResolverZones.json")

# Clients: which ISP resolver to use, and how apps reach their stub
**.dns                          = "10.0.0.2"     # NetworkStack binds dnsResolver.ispResolver = dns
*.*.resolver.ispResolver        = "10.0.0.3"     # (or set the stub's upstream directly)
*.client.hostedApp.resolverPath = "^.^.resolver" # app → local StubDnsResolver

# Retry / timeout on the client (DnsClientService)
**.dnsClient.maxAttempts     = 3
**.dnsClient.ticksForTimeOut = 5
**.dnsClient.timePerTick     = 200ms

Records are not strings in the INI — zones are plain JSON loaded with readJSON. For example DnsZone.json:

DnsZone.json 
[
  {
    "zone": "us-east-1.com",
    "records": [
      { "domain": "*.us-east-1.com",    "type": "A",     "ip":   "10.1.0.5" },
      { "domain": "test.us-east-1.com", "type": "CNAME", "text": "us-east-1.com" }
    ]
  }
]

Dynamic Registration

Zones don't have to be static. A service or orchestrator can register (or update/remove) its own record at runtime over a small RESTful API, so names become resolvable as soon as the service comes up.

Common Use Cases

Service Discovery for Cloud Provider

Fog nodes and edge devices discover the cloud provider manager service using DNS lookups instead of hardcoded IPs, allowing flexible infrastructure changes without reconfiguration.

Fog Node Mesh Discovery

Fog nodes discover peer nodes dynamically for workload forwarding and load balancing. DNS enables flexible mesh topology management.

Multi-Tenant Service Isolation

Different tenants or experiments can use separate DNS zones, isolating their services while sharing the same physical infrastructure.

Load Balancing via DNS

Multiple A records for the same domain name can distribute load across service replicas. DNS round-robin enables simple load distribution strategies.

Failure modes & caching

DNS is a control plane: when it misbehaves, the symptoms usually show up elsewhere. The most important effects to model are stale caches and the gap between resolution and reachability.

Stale cache after migration

Where resolution breaks

① Stale cache after migration

A service moves but clients keep the old cached IP. With no TTL, requests fail until the cache is explicitly invalidated.

④ DNS resolves but traffic fails

Resolution returns a valid IP (NOERROR) the routing layer can't reach — wrong subnet, lost wireless. The failure is at the network layer.

② Resolver as a single point of failure

If the ISP resolver is down or unreachable, every client's lookups time out and many unrelated services appear broken at once.

③ Incorrect zone → NXDOMAIN

A misnamed zone or malformed JSON makes specific domains always return NXDOMAIN. Check the ROOT→TLD→AUTH structure and wildcard syntax.

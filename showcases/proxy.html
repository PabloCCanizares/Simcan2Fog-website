Proxy & DNS Showcase

AppProxy Module & DNS-Based Service Discovery

Overview

The Proxy & DNS showcase demonstrates the AppProxy module and DNS-based service discovery from the Simcan2Fog simulator. It provides two configurations that illustrate how services are resolved and routed at the application layer.

Key Concept: Application-Layer Service Routing

The AppProxy acts as a reverse proxy inside each host, accepting TCP connections on port 443, extracting service names from request headers, and routing traffic to the appropriate backend via the ServiceTable. When DNS is enabled, domain names are resolved through a full recursive DNS chain before reaching the proxy.

NoDNS (ProxyNet)

Minimal 2-node configuration using direct IP addressing. Client connects to 10.0.0.1:443 and AppProxy resolves the service name via its local ServiceTable.

showcases/Proxy/ProxyNet

DNS (ProxyNet2)

Extended 4-node configuration with FQDN resolution. Client uses test.us-east-1.com, which is resolved through a recursive DNS chain before reaching the proxy.

Key Components

SimplifiedHost

Extends StandardHost with three additional submodules:

hostedApp

The user application module (e.g., UserAppModule)

proxy

AppProxy instance listening on port 443

serviceTable

Maps service names to IP:port endpoints

DnsSimplifiedHost

Extends SimplifiedHost by adding a DnsResolver submodule. Used by the client in the DNS configuration to resolve FQDNs before connecting to the proxy.

AppProxy

Application-layer gateway that accepts TCP connections on port 443, extracts service names from RestfulRequest host headers, queries the ServiceTable, and routes traffic to the appropriate backend.

Connection Types: PASSTHROUGH (outgoing/client-side) and EDGE (incoming/server-side).

AppProxy Session Lifecycle

Each proxied connection goes through three states:

1

INIT

A new TCP connection arrives on port 443. AppProxy accepts it and waits for the first request to determine the target service name.

2

PENDING

The service name has been extracted from the host header. AppProxy queries the ServiceTable via selectIp() and initiates a backend TCP connection.

3

ESTABLISHED

Backend connection is established. Data flows bidirectionally between client and backend through the proxy. The session remains open until either side closes the connection.

ServiceTable

The ServiceTable is a passive module (no gates, C++ API only) that maps service names to vectors of ServiceEntry (IP + port packed in a 64-bit value).

Registration

Services register via ProxyServiceRequest(REGISTER). Each entry maps a service name to one or more IP:port endpoints.

Load Balancing

When multiple endpoints exist for a service, selectIp() performs uniform random selection across the available entries.

Domain suffix stripping: The ServiceTable strips the configured domain suffix (default: "localdomain") from incoming service names before lookup. No TTL or expiry - entries persist until explicitly unregistered.

DNS Resolution Chain

In the DNS configuration, domain name resolution follows a three-level chain:

1

StubDnsResolver (Client)

The client's local DnsResolver sends the query for test.us-east-1.com to the configured resolver at 10.0.0.3.

2

DnsResolverServer (10.0.0.3, Recursive)

Consults ResolverZones.json which contains an NS record: us-east-1.com → 10.0.0.2. Forwards the query to the authoritative server.

3

DnsSimplified (10.0.0.2, Authoritative)

Consults DnsZone.json containing a wildcard A record: *.us-east-1.com → 10.0.0.1. Returns the server IP to the resolver, which forwards it back to the client.

DnsZone.json (Authoritative) 
// Wildcard A record
{
  "name": "*.us-east-1.com",
  "type": "A",
  "value": "10.0.0.1"
}
ResolverZones.json (Recursive) 
// NS record for delegation
{
  "name": "us-east-1.com",
  "type": "NS",
  "value": "10.0.0.2"
}

Configuration

NoDNS Configuration

showcases/Proxy/omnetpp.ini [NoDNS] 
# Network
network = ProxyNet

# Client: connect to server by direct IP
*.client.hostedApp.servingHost = "10.0.0.1"

# Server: register service name "test"
*.server.hostedApp.serviceName = "test"

DNS Configuration

showcases/Proxy/omnetpp.ini [DNS] 
# Network
network = ProxyNet2

# Client: connect using FQDN
*.client.hostedApp.servingHost = "test.us-east-1.com"

# Client DNS resolver
*.client.dnsResolver.address = "10.0.0.3"

# Server: register service name "test"
*.server.hostedApp.serviceName = "test"

# DNS infrastructure
*.dns.zoneFile = "DnsZone.json"
*.resolver.zonesFile = "ResolverZones.json"

What to Observe During Execution

Monitor these key behaviors to verify the showcase is working correctly:

  • • TCP connection to port 443 on the server's AppProxy
  • • Session state transitions: INIT → PENDING → ESTABLISHED
  • • ServiceTable lookup via selectIp() for service name resolution
  • • DNS config: UDP queries to 10.0.0.3 (resolver) and then to 10.0.0.2 (authoritative)
  • • DNS config: Wildcard A record match for *.us-east-1.com
💡

Design Rationale

This showcase is designed to isolate and demonstrate the proxy and DNS subsystems:

DNS vs ServiceTable

DNS resolves domains to IPs (network layer). ServiceTable resolves service names to endpoints (application layer). Both work together for full service discovery.

Incremental Complexity

NoDNS shows the proxy in isolation. DNS adds the full resolution chain. This progressive approach helps understand each layer independently.

Data Centre Showcase

VM Provisioning & Control Plane Operations

Overview

The Data Centre showcase demonstrates the SIMCAN control plane for VM provisioning and application deployment. It showcases how an EdgeUser requests a VM in a specific zone (e.g., "us-east-1") from the CloudProvider, and once the VM is ready, deploys a remote application on it.

Key Concept: MessageQueue as Control Plane Highway

The MessageQueue serves as the central bus for all control plane operations. Everything related to "create VM", "deploy app", "notify settings" travels through it using SIMCAN_Message with topic-based routing.

DcShowcase

Basic scenario: EdgeUser requests VM and deploys a remote application (CPU-intensive workload).

showcases/Datacentre/DcShowcase

EdgeDcShowcase

Extended scenario: Deploys both remote service and local app (on Raspberry Pi) with dependency management.

showcases/Datacentre/EdgeDcShowcase

Network Topology

The showcase uses a deliberately simple topology to focus on control plane logic without routing complexity. All components connect to a central Ethernet switch forming a flat LAN. 

                  EthernetSwitch (Central)
                          |
       ┌──────────┬──────────┬──────────┬──────────┐
       |          |          |          |          |
  MessageQueue CloudProvider DataCentre   DNS   DcUsers[i]

Connection Details

  • MessageQueue (10.0.0.1): Ports 8444 (push) and 8443 (pull/ack)
  • DNS (10.0.0.2): Simplified DNS service
  • DnsResolverServer (10.0.0.3): DNS resolution delegation
  • DataCentre.stack (10.0.0.4): Compute and storage backend
  • DcUsers[*]: Dynamic IPs assigned via networkSettings.xml

Key Components

DcUser / DcEdgeUser

These are packaged user modules containing:

  • • EdgeUser: Business logic for VM requests, app deployment, and workflow coordination
  • • NetworkStack: SIMCAN ↔ TCP/IP adapter with QueueClient and DnsResolver
  • • Raspberry5 (EdgeDcShowcase only): Local controller connected via serial for edge applications

Important: Each user has a unique topic for consuming responses:

networkStack.nodeTopic = fullName();

NetworkStack

Bridges SIMCAN control messages with TCP/IP transport:

QueueClient - Push

Sends messages to topics (e.g., "cloudProvider")

QueueClient - Pull

Listens on own topic for responses

MessageQueue (Broker)

The central message broker implementing topic-based pub/sub:

  • • MessageQueueIn (8444): Accepts push messages from producers
  • • MessageQueueOut (8443): Serves pull/ack requests from consumers
  • • topicToQueueMap: FIFO queues per topic
  • • Delivery: 1 message per ACK (SM_QueueAck)

CloudProvider

The scheduler/orchestrator responsible for:

  • • Receiving VM/app requests from users via topic "cloudProvider"
  • • Resource allocation decisions based on zone, capacity, and policies
  • • Coordination with DataCentre for VM instantiation
  • • Response routing back to user's return topic

DataCentre

Represents the physical compute pool with detailed resource modeling: 

# Data Centre Profile
*.dataCentre.blades = 4
*.dataCentre.cores_per_blade = 16
*.dataCentre.ram_per_blade = 64GB
*.dataCentre.disk_per_blade = 4000GB
*.dataCentre.zone = "us-east-1"
*.dataCentre.domain = "us-east-1.com"

The domain parameter is crucial for service endpoint resolution via DNS.

DNS Components

Two-level DNS modeling for service discovery:

dnszone.json

*.us-east-1.com → 10.0.0.4

resolver.json

Delegates us-east-1.com from .com

Execution Workflow

Step-by-step flow from VM request to application deployment:

1

Initialization

EdgeUser.initialize() loads:

  • • Deployment zone (e.g., "us-east-1")
  • • VM list from omnetpp.ini
  • • Local and remote application definitions
  • • Dependency map (if using dependsOn)
2

VM Request

For each VM definition:

  • • Creates SM_UserVM with SM_VM_Req
  • • Sets zone = "us-east-1"
  • • Sets destinationTopic = "cloudProvider"
  • • Sends via queueOut → NetworkStack → PushClient
3

MessageQueue Transit

Control plane message routing:

  • • PushClient wraps in TCP packet → LAN → MessageQueue (10.0.0.1:8444)
  • • MessageQueueIn receives and enqueues to "cloudProvider" topic
  • • Waits for consumer ACK
4

CloudProvider Processing

Scheduler consumes and decides:

  • • Sends SM_QueueAck("cloudProvider")
  • • Receives 1 VM request message
  • • Coordinates with DataCentre for resource reservation
  • • Returns response to user's returnTopic
5

Application Deployment

User receives VM_Response and proceeds:

  • • Marks VM as UP
  • • Prepares SM_UserAPP for remote applications
  • • Sends deployment request to assigned VM/hypervisor topic
6

Dependency Resolution (EdgeDeployment)

When remote service is UP:

  • • Calls sendServiceIsUp()
  • • Composes serviceName = "<service>.<domain>"
  • • Sends SM_AppSettings to local app (via serial → Raspberry)
  • • ProbingEndpoint starts DNS resolution and connection

Workload Configuration

Virtual Machines (vms.json)

VM types are defined in vms.json with resource profiles:

vms.json 
// Example VM types
{
  "type": "VM_large",
  "cores": 4,
  "memory": 8192, // MB
  "disk": 100 // GB
}

omnetpp.ini configuration:

*.dcUsers[*].edgeUser.vms = [{"name":"vm-us-east-1", "type":"VM_large"}]

Applications (apps.json)

DcShowcase

Remote CPU-intensive application:

remoteApps = [{
"name": "huge-calculation",
"type": "AppCPUIntensive",
"platform": "vm-us-east-1"
}]

EdgeDcShowcase

Remote service + Local client:

remote: "ServiceEndpoint"
local: "ProbingEndpoint"
dependsOn: "myservice"

Dependency Mechanism: The local app doesn't know the serviceName until the remote service is UP, enforcing proper orchestration order.

Configuration Example

showcases/Datacentre/omnetpp.ini 
# Network Configuration
network = DcShowcase

# Number of Users
*.numDcUsers = 2

# User Configuration
*.dcUsers[*].networkStack.nodeTopic = "${fullName()}"
*.dcUsers[*].edgeUser.deploymentZone = "us-east-1"
*.dcUsers[*].edgeUser.vms = [{"name":"vm-us-east-1", "type":"VM_large"}]
*.dcUsers[*].edgeUser.remoteApps = [{"name":"huge-calculation", "type":"AppCPUIntensive", "platform":"vm-us-east-1"}]

# MessageQueue Configuration
*.messageQueue.address = "10.0.0.1"

# CloudProvider Configuration
*.cloudProvider.networkStack.nodeTopic = "cloudProvider"

# DataCentre Configuration
*.dataCentre.zone = "us-east-1"
*.dataCentre.domain = "us-east-1.com"
*.dataCentre.blades = 4
*.dataCentre.cores_per_blade = 16
*.dataCentre.ram_per_blade = 64 # GB
*.dataCentre.disk_per_blade = 4000 # GB

# DNS Configuration
**.dns = "10.0.0.2"
*.dnszone.file = "dnszone.json"
*.resolver.file = "resolver.json"

Showcase Variants

DcShowcase - Basic

Demonstrates the fundamental VM provisioning and remote application deployment workflow.

  • ✓ EdgeUser requests VM from CloudProvider
  • ✓ VM provisioned in DataCentre with zone "us-east-1"
  • ✓ CPU-intensive application deployed on VM
  • ✓ All control plane traffic via MessageQueue

EdgeDcShowcase - Advanced

Extends the basic scenario with edge computing, local applications, and dependency management.

  • ✓ Remote ServiceEndpoint deployed in DataCentre
  • ✓ Local ProbingEndpoint on Raspberry Pi controller
  • ✓ Dependency resolution via SM_AppSettings over serial
  • ✓ DNS-based service discovery (*.us-east-1.com → 10.0.0.4)
  • ✓ Local app starts only after remote service is UP
🔍

What to Observe During Execution

Monitor these key behaviors to verify the showcase is working correctly:

  • • TCP traffic to 10.0.0.1:8444 (push) and 10.0.0.1:8443 (pull/ack)
  • • Periodic SM_QueueAck messages from consumers (CloudProvider, users)
  • • EdgeDcShowcase: SM_AppSettings messages over serial to Raspberry5
  • • EdgeDcShowcase: DNS resolutions to 10.0.0.2 for service discovery
  • • EdgeDcShowcase: ProbingEndpoint connections to remote ServiceEndpoint
💡

Design Rationale

This showcase is deliberately designed to separate concerns with surgical precision:

Data Plane

Real Ethernet/IP for endpoints, DNS queries, and application traffic. Uses standard TCP/IP networking.

Control Plane

SIMCAN_Message over MessageQueue using topic-based routing. Keeps orchestration separate from data.

By using a flat LAN topology, routing complexity is eliminated, allowing you to focus on debugging control plane logic without network noise.
